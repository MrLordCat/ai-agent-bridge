# Производительность и сбои инструментов — 2026-10-20

Дополнение 1.18.14: при проверке общей подготовки контекста найден и исправлен
квадратичный поиск путей в многомегабайтной строке генератора сводки. Это
подтверждённый сценарий зависания Extension Host; подробности и регрессия —
в [описании общего контекста](SHARED_CONTEXT.md). Измерения ниже относятся к
более раннему baseline 1.18.13.

Исследована локальная разработческая версия 1.18.13. Измерения проведены на
Windows, Core Ultra 7 258V, 32 ГБ RAM, установленном VS Code 1.141.1.
Числа и точная версия Node сохранены в [JSON](performance-2026-10-20.json).

Постоянная высокая загрузка CPU в ходе проверки **не воспроизведена**. В снимке
`code --status` рабочий Extension Host занимал около 1 011 МБ при 0% CPU;
renderer рабочего окна — около 1 277 МБ при 4% CPU. Это показатели процессов
со всеми расширениями и открытым большим чатом, а не память одного Bridge.
Такой снимок не исключает всплесков во время генерации.

## Подтверждённые причины сбоев

### Coco: SDK callback истекает через 30 секунд

В `coco.log`, native session `51bf6b6a-9b78-411a-8903-d19b647203b6`,
19 октября в 19:03–19:05 UTC три вызова (терминал Coco, общий терминал,
`read_file`) завершились `Control request timed out after 30000ms`.
CLI `sdkMcpRegistry.callTool` вызывает `StructuredInput.sendRequest` без
переопределения его фиксированного значения 30 000 мс. В этот срок входят
подтверждение пользователя, выполнение инструмента и возврат результата Chat.

Отдельный callback без действий возвращал случайный маркер после 35 секунд:

| Путь | Вызовов | Время callback | Время запроса | Маркер получен |
| --- | ---: | ---: | ---: | --- |
| SDK | 1 | 35 004 мс | 52 635 мс | нет |
| ACP | 1 | 35 004 мс | 43 532 мс | да |

Быстрый SDK callback проходит; текстовый ответ и исправленные имена инструментов
не проверяют этот сценарий ожидания. Эти длительности запросов включают сеть и
модель; это не измерение локального CPU и не сравнение скорости моделей.

Исправление: запросы Coco с инструментами VS Code используют ACP. Сохраняются
нативная история, `session/load`, session ID и выполнение через карточки Chat.
При добавлении инструментов после SDK-хода завершённая сессия закрывается и
загружается через ACP с тем же ID. Повторной отправки всей истории нет.
Для текстовых запросов без инструментов остаётся выбор SDK/ACP.

Дополнительно проверен настоящий `CocoChatModelProvider` в установленном VS Code:
он отдал один вызов в Chat, получил результат через 35 секунд и завершил тот же
native prompt с правильным маркером (60,4 с вместе с запуском и моделью).
В этой проверке исполнение инструмента имитируется внутри теста провайдера;
интерактивное нажатие кнопки подтверждения пользователем не автоматизировалось.

Воспроизводитель: `scripts/coco-tool-latency-repro.mjs`. Без `--run` запросов
к модели нет. С `--run --cli PATH --transport sdk|acp --delay-ms 35000` выполняется
только callback с маркером, без команд модели. Скрипт намеренно использует
исходный SDK напрямую, чтобы сохранять возможность воспроизвести его ограничение.

### Cursor: холодный перенос длинного чата

Сохранённая ошибка: попытка отправить 2 148 837 символов при лимите холодной
истории 64 000; причина привязки `new_conversation`. Запрос на сервер не ушёл.
Это другая причина, чем прежний `Premature close` после выполнения инструмента.

Исправление: структурированная история локально сокращается в пределах прежнего
лимита. Последний запрос и его текущие изображения сохраняются целиком, полный
оригинал записывается в архив, Chat показывает путь и отправляемый объём.
После завершения работают обычные native checkpoint и последующие дельты.
Слишком большой текущий запрос, более пяти текущих изображений, неизвестный
формат промпта или ошибка native resume по-прежнему останавливают inference.

Регрессия проверяет перенос >2 млн символов, полный архив, один SDK send,
целый текущий запрос и последующий reload без повторного prefill.
Ответ настоящего сервера Cursor в этом исследовании не проверялся.

## Измерения локальной обработки

Запускается тест `Extension performance research` с `AAB_PERF_RESEARCH=1`.
`AAB_PERF_REPORT` задаёт путь для JSON. По умолчанию тест пропущен и не создаёт
нагрузку обычному прогону. Обращений к моделям в benchmark нет.

История синтетическая, преимущественно текстовая. Один цикл журнала —
`ConversationHistory.begin` и `complete`, то есть два атомарных сохранения.

| Размер истории | 5 циклов журнала, время / CPU | 20 слияний, время / CPU |
| --- | ---: | ---: |
| 100 тыс. символов | 49,7 / 79 мс | 14,0 / <разрешения счётчика мс |
| 1 млн | 120,2 / 110 мс | 145,9 / 124 мс |
| 3 млн | 206,0 / 188 мс | 356,3 / 343 мс |

При 3 млн символов это около 41 мс на полный цикл журнала и 18 мс на слияние.
Пять циклов переписывают суммарно примерно 30 МБ JSON. Изменение RSS за эту
серию составило +23,5 МиБ; это не peak и не доказательство утечки. GC может
делать дельту отрицательной. CPU измерен для всего тестового Extension Host,
имеет ограниченное разрешение и может включать фоновые действия расширений.
Это ориентир одного прогона, не статистическая оценка p95.

10 000 последовательных текстовых чанков в `CocoTurnMetrics.accept` заняли
1,48 мс и породили одно обновление: уже работает ограничение публикации 250 мс.
Benchmark не включает IPC и отрисовку самого Chat; реальный поток длится дольше
250 мс и публикуется неоднократно.

100 сериализаций Live Report на максимальных 500 записях заняли 101 мс
(126 мс CPU), размер одного JSON — 540 371 байт. Текущий реальный отчёт был
92 758 байт / 8 записей. Одна сериализация сама по себе не объясняет высокую
постоянную загрузку, но остаются стоимость записи, IPC и отрисовка webview.

## Где ускорять дальше

1. **Сохранение истории и ключи сообщений.** `ConversationHistory.begin` каждый
   раз кодирует/хэширует прежние и входящие сообщения; `persist` целиком
   сериализует историю до и после каждого model-provider сегмента, включая
   возврат инструментов. Рассмотреть журнал дельт с периодическим атомарным
   snapshot и повторное использование ключей неизменившихся сообщений.
   Сначала проверить инвалидацию при правках, ветвлении, изменении tool result,
   изображениях и параллельных lease. Простой пропуск сохранения может потерять
   историю при смене провайдера или reload.
2. **Обновления отчёта.** Комментарий в `extension.ts` говорит о завершённых
   ходах, но подписка `sessionQuality.onDidChange` срабатывает и на живых
   `updateTurn`. Каждое событие запускает полную запись JSON и обновление
   webview, без единой очереди записей. Нужны объединение обновлений, один
   writer и гарантированный последний snapshot. Для CPU-приоритета нужен trace:
   измеренная сериализация обходится примерно в 1 мс, не в сотни миллисекунд.
3. **Renderer и Quick Access.** `quickActionsProvider.refresh()` обновляет всё
   дерево, а Live Report получает все записи при каждом событии. Измерить
   Chromium Performance при реально открытом отчёте; затем обновлять текущую
   запись и затронутые узлы. Не выводить нагрузку renderer из Node benchmark.
4. **Холодный prefill.** Даже быстрый локальный архив не отменяет сетевую
   задержку и обработку большого контекста моделью. Приоритет — надёжные
   нативные привязки и небольшие новые дельты. Увеличение лимита отправки само
   по себе не ускоряет работу. Добавлены `sessionPrepareMs`, `historyPrepareMs`,
   `coco.tool.delegated` / `coco.tool.returned` для разделения этапов без
   содержимого промптов и аргументов инструментов.
5. **Опрос недоступных источников.** В журнале регулярно повторяются ошибки
   локального `localhost:8000`. Для неиспользуемого источника полезны backoff
   или явное отключение. Нагрузка от этого в текущем замере не выделена.

Для следующего точного CPU-профиля нужен trace Extension Host и renderer в
интервале наблюдаемой пользователем высокой нагрузки, с указанием модели,
открытых панелей и PID. Текущие факты не позволяют назвать один компонент
единственной причиной. Оптимизации сохранения/отрисовки перечислены как
следующие шаги; в этом патче изменено поведение двух подтверждённых сбоев.
