# Cursor: разбор cache hit 70,04%

Проверено 2026-10-16 на локальном журнале SDK 1.0.37, модель
`claude-opus-5-5`. При диагностике сеть для SDK была запрещена;
запросов генерации не выполнялось, исходное хранилище не изменялось.

Запрос расширения `cursor-12897d90-5640-4a00-a0bd-0542009c38d5`
соответствует native `run-157eca43-0ebb-4989-b9d6-7ee3bb0aabd7`.
Он продолжил того же агента, что предыдущие запросы. Его start checkpoint
совпадает с последним завершённым checkpoint run 10; промежуточный run 11
завершился ошибкой. Ошибка восстановления сессии в этом случае не подтверждена.

## Что означают счётчики

| Счётчик | Токены |
|---|---:|
| Обработанный вход за весь native run | 1 280 952 |
| Прочитано из кеша | 897 178 |
| Записано в кеш | 383 744 |
| Вход без cache read/write | 30 |

Hit = 897 178 / 1 280 952 = **70,04%**. Формула расширения корректна.
SDK input уже включает cache read/write; его totalTokens может прибавлять
кеш повторно и в вычислении не используется.

383 744 cache-write токена означают обработку с записью кеша. Это не измерение
числа потерянных старых токенов: сюда может входить новый материал.
Нулевой coldRewriteTokens в прежнем JSON был значением по умолчанию при
отсутствии детализации, а не доказательством отсутствия повторной записи.

SDK сохранил ровно одно usage-событие на этот native run, при этом в нём
14 завершённых вызовов инструментов, 7 thinking и 8 assistant steps.
Эти steps не дают точного числа модельных обращений. В JSON 1.18.3
modelSegments: 1 обозначал один SDK run, а не один запрос к модели.
Отдельных cache counters первого обращения и продолжений в журнале нет.

Общий размер сериализованных аргументов инструментов — 9 149 символов,
результатов — 11 839 символов. Результаты инструментов этого run сами по себе
не объясняют объём cache writes. Размер входного продолжения, добавленного
перед run, старая версия не сохраняла; возможный вклад истории ошибочного
run 11 отдельно по этим данным не измерен.

## Сравнение той же native-сессии

Пауза считается от завершения run, чей checkpoint реально использован
в качестве start checkpoint.

| Native turn | Пауза, минуты | Cache read | Cache write, токены |
|---|---:|---:|---:|
| 7 | 318,40 | 93,46% | 227 148 |
| 8 | 848,49 | 79,79% | 238 752 |
| 9 | 14,00 | 74,95% | 244 656 |
| 10 | 5,47 | 88,63% | 264 643 |
| 12 — проблемный | 72,42 | 70,04% | 383 744 |

Наблюдение совместимо с повторным созданием большого префикса после паузы
и последующим чтением внутри run. В длинном run 7 получилось 93,46% при
значительных cache writes: общий процент зависит также от числа внутренних
продолжений и их объёма. Сравнение процентов разных задач без этой детализации
не показывает, насколько хорошо кешировалось первое обращение.

Наиболее вероятный вклад — обновление большого накопленного префикса после
паузы; альтернативы включают изменение системного/инструментального префикса
и новые записи входной истории. Серверные TTL, eviction, маршрутизация и
точки кеширования Cursor здесь не сообщаются. Установить конкретную причину
истечения или перестройки кеша по одному агрегату нельзя. Сохранённый native
checkpoint не фиксирует серверный prompt cache.

## Диагностика начиная с 1.18.4

В скопированном JSON cache.cursor содержит:

- usageScope: native-run-aggregate и modelCallBreakdown: unreported;
- nativeRunId и причину сопоставления истории sessionReason;
- sentTextChars, sentMessages и sentImages — объём реально отправленного
  продолжения, включая обёртку расширения; это не полный native контекст;
- toolCatalogHash и toolCatalogChanged — сравнение эффективных SDK descriptions
  и schemas с предыдущим завершённым run; порядок ключей и функции callbacks
  исключены, тексты инструментов в журнал не копируются;
- toolCatalogChangesDuringRun — изменения при возврате tool results;
- compactionStatus: unreported и uncachedInputTokens.

В cache.sdkRuns находится число SDK runs; modelSegments и coldRewriteTokens
остаются неопределёнными без соответствующих данных. Поле compacted не
заполняется выдуманным false. Низкий hit восстановленной сессии классифицируется
как unknown; сам факт восстановления остаётся в sessionMode.

performance.gapSinceLastResponseMs измеряется по сохранённому времени завершения.
Первые запросы со старыми checkpoint не имеют этой метрики и предыдущего
fingerprint. Следующий завершённый запрос сохраняет их для сравнения после reload.
Эти поля позволят отличить большой новый ввод, изменение каталога и длительную
паузу, но не докажут серверную причину eviction. Автоматический keep-alive
не добавляется: он сам расходовал бы модельные запросы без гарантии cache hit.

Проверки 1.18.4: 728 passing / 8 pending на VS Code 1.131.0;
726 passing / 10 pending на установленной VS Code 1.141.0.
TypeScript, ESLint, metadata и git diff --check прошли. Отдельно проверены
реальные числовые counters из этого случая, сравнение schemas с перестановкой
ключей, сохранение fingerprint и времени после reload, а также JSON панели.
