# Аудит унификации AI Agent Bridge 1.17.12

Дата: 2026-10-14. Базовый коммит: `c5a6f6e`.

Цель: уменьшить число мест, которые приходится менять при добавлении
провайдера, и вынести повторяющиеся механизмы в проверяемые общие компоненты.
Это статический аудит регистрации, маршрутизации, контекста, инструментов,
каталогов, состояния и UI. Он не является полным аудитом безопасности.
Перед коммитом прошли 651 тест, линтер и проверка ошибок редактора; аудит
не меняет исполняемый код. Указанные ниже риски миграции не означают, что
каждый из них воспроизведён как ошибка в работающем расширении.

Основная рекомендация: общий реестр экземпляров провайдеров, нормализованные
метаданные и состояние, затем общие механизмы кеширования и продолжения
вызовов инструментов. Различия HTTP, SDK, ACP и app-server должны оставаться
в адаптерах протоколов.

## Приоритеты

P1 — наибольшая отдача для расширяемости; P2 — унификация поведения и данных;
P3 — поддержка последующих изменений. Это приоритеты рефакторинга.

| Приоритет | Область | Наблюдение | Рекомендуемая граница |
|---|---|---|---|
| P1 | Регистрация и маршрутизация | Состав провайдеров повторяется в нескольких слоях | `ProviderRegistry` и дескрипторы источников |
| P1 | Вызовы инструментов | Четыре реализации ожидания и продолжения вызовов | Общий контроллер реплики с адаптерами результатов |
| P1 | Оркестрация API-источников | HTTP и Cursor SDK собраны внутри Llama.cpp-провайдера | Фасад источников и самостоятельные адаптеры транспорта |
| P2 | Метаданные и контекст | Несколько способов строить лимиты и настройки модели | `ModelDescriptor` и общий адаптер к VS Code |
| P2 | Кеши и обновление | TTL, объединение запросов и инвалидация реализованы отдельно | `AsyncResourceCache` с поколением конфигурации |
| P2 | Состояние, usage и UI | 32 аргумента UI, отдельные формы usage, два типа источников метрик | `ProviderSnapshot`, типизированный usage и метрики по source ID |
| P3 | Проверки контрактов | Общие гарантии проверяются отдельными тестами интеграций | Набор контрактных тестов для каждого адаптера |

## 1. P1: реестр источников вместо нескольких списков провайдеров

Доказательства:

- [CompositeChatModelProvider](../src/composite-provider.ts#L17) принимает
  фиксированные default/Codex/Claude/Coco аргументы; `selectProvider` отдельно
  распознаёт их ID и направляет остальные ID в default provider.
- [ProviderDirectoryOptions](../src/providers/provider-directory.ts#L63)
  содержит отдельные функции статуса Codex, Claude и Coco;
  [refresh](../src/providers/provider-directory.ts#L213) перечисляет их снова.
- [groupProviderModels](../src/ui/provider-model-picker.ts#L25) повторяет
  распознавание префиксов, подписи провайдеров и группировку.
- [activate](../src/extension.ts#L601) вручную создаёт и связывает провайдеры,
  а [подписки на статус](../src/extension.ts#L692) повторяют одну последовательность
  обновления Directory, Quick Access и Providers Manager.

Следствие: добавление интеграции требует синхронных изменений маршрутизации,
статусов и представлений. Неизвестный префикс модели получает HTTP-маршрут
по умолчанию, а не явную ошибку отсутствующего владельца.

Предложение: регистрировать дескриптор экземпляра источника с устойчивым ID,
названием, принадлежностью моделей, адаптером транспорта, состоянием и
поддерживаемыми действиями. Composite, Directory и выбор моделей должны
получать свои списки из этого реестра. Один профиль API остаётся одним
экземпляром источника; тип транспорта отделён от идентичности профиля.

Сохранять существующие `codex::`, `claude::`, `coco::` и `api-{id}::` ID
через совместимые резолверы. Cursor остаётся существующим API-профилем:
общий реестр не должен создавать дополнительный переключатель или хранилище
его ключа. Проверки: совпадающие названия профилей, отключённые профили,
неизвестный ID, частично недоступный каталог и изоляция ошибок discovery.

## 2. P1: общий контроллер продолжения вызовов инструментов

Доказательства:

- [CursorToolBridge](../src/cursor/tool-bridge.ts#L14): pending calls,
  граница ответа, attach/resume, очередь вывода, отмена и таймер.
- [CocoTurnBridge](../src/coco/turn-bridge.ts#L69): тот же цикл start/resume,
  проверка набора результатов, attach/detach и ограниченная очередь вывода.
- [CodexTurnBridge](../src/codex/turn-bridge.ts#L258): start/resume,
  pending calls и отдельная проверка полноты результатов.
- [ClaudeAppServerClient.resumeToolResults](../src/claude/app-server-client.ts#L581):
  attach, сопоставление call ID и разрешение ожидающих callback-вызовов.

Следствие: общие исправления отмены, повторного результата, потерянного
продолжения и завершения нужно переносить между интеграциями вручную.
При этом различия в планировании пакетных вызовов и таймерах существенны:
Cursor использует microtask и общий таймер, Coco — setImmediate и таймер
ожидания продолжения, Codex дополнительно восстанавливает состояние turn.

Предложение: компонент, отвечающий за pending calls, выдачу вызова один раз,
границу ответа, буферизацию и идемпотентное завершение. Стратегия группировки,
таймаута и полноты результатов задаётся явно. Кодеки SDK/ACP/app-server,
возобновление durable session, сверка состояния Codex и доставка нового
пользовательского сообщения в Claude остаются в адаптерах.

Начинать с Cursor и Coco после общего набора контрактных тестов. Проверки:
параллельные вызовы, частичный и повторный результат, поздний callback,
отмена до выдачи и во время ожидания, завершение без результата, смена
профиля/ключа/модели/чата и освобождение процесса. Вызовы по-прежнему
исполняются через нативный VS Code Chat с его подтверждениями.

## 3. P1: отделить оркестрацию источников от Llama.cpp-транспорта

Доказательства: [llama-provider.ts](../src/llama-provider.ts) содержит около
6,5 тысяч строк и обслуживает локальный сервер, DeepSeek и API-профили.
В [discovery](../src/llama-provider.ts#L3921) и
[respond](../src/llama-provider.ts#L4076) есть отдельные ветки Cursor,
переключающие выполнение на SDK/Cloud Agents. Объект Cursor и его
[dispose](../src/llama-provider.ts#L614) принадлежат Llama.cpp-провайдеру.

Следствие: добавление транспорта, который не является OpenAI HTTP API,
расширяет класс HTTP-провайдера и связывает независимые жизненные циклы.
Размер файла сам по себе не дефект; проблема — смешение ответственности.

Предложение: фасад API-источников выбирает адаптер по дескриптору реестра.
Адаптер предоставляет discovery, ответ, подсчёт токенов и lifecycle;
семейства HTTP-запросов сохраняют собственные настройки и capabilities.
`BaseChatModelProvider` остаётся реализацией механики OpenAI-стриминга.
Cursor SDK и ACP не должны наследовать его SSE-парсер ради формального
общего базового класса.

Выделять части по очереди, сохраняя публичный VS Code vendor, идентификаторы
моделей и настройки профилей. Проверять отсутствие изменения формы запросов,
обработки reasoning и поведения локального кеша.

## 4. P2: нормализовать модель, окно контекста и параметры

Доказательства:

- [ChatModelSource/LlamaCppModelInfo](../src/model-sources/source-routing.ts#L11)
  описывают общий источник через HTTP-поля и DTO Llama.cpp.
- [HTTP context resolution](../src/llama-provider.ts#L1808),
  [Cursor.models](../src/cursor/profile-transport.ts#L72),
  [Codex model adapter](../src/codex/model-adapter.ts#L60),
  [Coco model adapter](../src/coco/model-adapter.ts#L110) и
  [Claude discovery](../src/claude/claude-provider.ts#L2424)
  отдельно вычисляют входной и выходной лимиты и строят VS Code metadata.
- Reasoning schema собирается отдельно в Cursor, Codex, Claude и Coco;
  [ContextControlState](../src/ui/context-control.ts#L20) имеет отдельные
  поля и ветки настройки для конкретных провайдеров.

Предложение: нормализованный `ModelDescriptor` с source ID, native model ID,
максимальным окном, происхождением лимита (reported/observed/fallback),
выходным лимитом, рабочим cap, возможностями и поддерживаемыми параметрами.
Общий адаптер строит VS Code metadata и schema. Связь `reasoningEffort`
с оригинальным именем параметра и его допустимыми значениями сохраняется
в дескрипторе, а не угадывается по семейству.

Общими должны быть ограничения и преобразования, а не одинаковые числовые
дефолты. Резерв ответа и способ compaction задаются политикой транспорта.
Рабочий cap не увеличивает максимум; фактические Tools зависят также от
доступности runtime. Существующий `calculateContextBudget` использовать
для применимой арифметики, не заменяя им native compaction других runtime.
Проверки: отсутствующий максимум, изменение наблюдаемого окна, разные лимиты
моделей одного профиля, неизвестное значение reasoning и сохранение настроек.

## 5. P2: общий кеш асинхронного ресурса

Доказательства:

- [Cursor catalog](../src/cursor/profile-transport.ts#L58) имеет TTL и
  идентичность профиля, но не объединяет параллельные запросы каталога.
- [HTTP model discovery](../src/llama-provider.ts#L3761) отдельно объединяет
  in-flight запросы. Его [cache key](../src/llama-provider.ts#L1762)
  содержит только факт наличия ключа, а не поколение credentials.
- [ApiProviderService.getBalanceInfo](../src/api-providers/api-provider-service.ts#L287)
  реализует TTL, in-flight, force refresh и revision, защищающий от записи
  устаревшего ответа после изменения доступа.

Предложение: `AsyncResourceCache` с ресурсным ключом, TTL, объединением
запросов, явной инвалидацией и поколением конфигурации. Поздний ответ старого
поколения не публикуется. Не помещать исходный секрет в cache key или лог;
использовать revision credentials. Начать с переноса уже проверенной
механики ApiProviderService, затем подключить остальные каталоги.

Отдельно определить владение отменой: отмена одного потребителя общего
запроса не должна автоматически отменять остальных. Ошибка не заменяет
валидные данные ложным успешным значением. TTL и сохранение последнего
успешного результата задаются политикой ресурса. Обновление бюджета должно
оставаться независимым от перезапуска SDK-чата.

## 6. P2: единое состояние провайдера и точные типы usage

Доказательства:

- [LlamaQuickActionsProvider](../src/ui/quick-access.ts#L475) имеет 32
  позиционных аргумента; [activate](../src/extension.ts#L647) передаёт функции
  чтения отдельных полей Codex, Claude, Coco, DeepSeek и API-профилей.
- [resolveSubscriptionState](../src/providers/provider-directory.ts#L116)
  распознаёт паузу по тексту `summary.startsWith("Paused")`.
- [runtimeSourceForModel](../src/extension.ts#L65) имеет только `local` и
  `deepseek`, а также классифицирует по слову deepseek в имени модели.
  Результат используется для [context metrics](../src/extension.ts#L941)
  и [turn metrics](../src/extension.ts#L962). Обычная API-модель попадает
  в local; DeepSeek-модель другого API-профиля попадает в deepseek.
- [ApiProviderBalanceInfo](../src/api-providers/balance.ts#L21) отдаёт в UI
  текстовые summary/rows. Историческая реализация Cursor budget (удалена в 1.17.15)
  представляет лимит допрасходов, а не то же самое, что monthly usage плана.

Предложение: `ProviderSnapshot` со стабильным source ID, типизированным
статусом, capabilities, actions, `ProviderRuntimeMetrics` и usage.
Quick Access и Manager читают один снимок. Начальный небольшой шаг —
заменить позиционные аргументы объектом зависимостей; затем переносить
представления на общий snapshot и renderer с расширениями для провайдеров.

Метрики хранить по source ID, не по имени семейства модели. Состояние paused
передавать отдельным значением, независимо от текста и языка UI. Usage
должен различать credits balance, spending cap, included monthly usage,
rolling quota и стоимость конкретного запуска. Числа, единица/валюта,
период, reset time, источник и состояние unavailable хранятся как данные;
подписи и строки форматирует UI.

Для Cursor разнести API-адаптер командного бюджета и потенциальный адаптер
dashboard usage. Доступ к `GetCurrentPeriodUsage` пользовательским API-ключом
пока не подтверждён реальным авторизованным запросом в этом аудите. Наличие
RPC/schema в SDK не является подтверждением доступа или точного совпадения
полей с дашбордом. Общая форма usage не должна скрывать эту неопределённость.

## 7. P3: контрактные проверки общего поведения

Сейчас гарантии продолжения, отмены и каталога проверяются в отдельных
наборах, например [Cursor tools](../src/test/cursor-tools.test.ts),
[Coco tools](../src/test/coco-tools.test.ts),
[Codex](../src/test/codex.test.ts) и
[provider catalog](../src/test/provider-catalog.test.ts).

Предложение: общий набор сценариев, который запускается через небольшой
тестовый адаптер каждого транспорта. Он проверяет принадлежность модели,
сохранение профиля, инвалидацию каталога, Tools/Ask, выдачу вызова один раз,
продолжение, отмену и завершение. Специфичные проверки формы SSE/ACP/RPC,
durable session, reasoning, images и авторизации остаются отдельными.
Тесты должны проверять поведение и границы адаптера, а не повторять его код.

## Порядок внедрения

1. Добавить контрактные сценарии для текущего поведения и совместимости ID.
2. Ввести реестр поверх существующих провайдеров; перевести Composite,
   Directory и группировку моделей на него без изменения транспорта.
3. Ввести ModelDescriptor/ProviderSnapshot, перевести метрики на source ID
   и убрать позиционные зависимости Quick Access. Сохранить адаптер старых настроек.
4. Вынести общий кеш, начиная с бюджета; добавить проверки старого ответа
   после refresh и независимой отмены потребителей.
5. Отделить фасад API-источников от OpenAI/Llama.cpp транспорта.
6. Перенести Cursor и Coco на общий контроллер инструментов; после проверок
   мигрировать общую механику Claude и Codex, сохранив их runtime-особенности.

Критерий результата: новая интеграция добавляется адаптером и регистрацией
дескриптора. Маршрутизация, группировка, базовые статусы и метрики начинают
работать без новых веток по имени провайдера в нескольких слоях. Существующие
профили, ключи, выбранные модели и сценарии продолжения сохраняются.
