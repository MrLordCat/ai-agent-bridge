# Coco: продолжение чата и учёт кеша

Реализовано в 1.17.16. Проверено 2026-10-15 на Windows, Cortex Code
v0.26.1015 из Snowflake VS Code 1.42.2, модель `claude-opus-5-5`.

## Переключение Codex → Coco

Общий маршрутизатор сохраняет видимую историю Chat в локальном журнале
workspace: пользовательские сообщения, ответы, вызовы/результаты инструментов
и изображения. При переходе на Coco он объединяет текущую историю VS Code
с уже полученными сообщениями, которые новый renderer мог не включить из-за
меньшего бюджета. Скрытые рассуждения провайдеров не копируются.

Внутри Coco действует отдельная нативная сессия для сочетания workspace,
conversation ID, модели, CLI и Snowflake connection. Повторный запрос отправляет
новые сообщения. Если между ними работал Codex, его новые сообщения и результаты
также добавляются. Редактирование/перемотка истории начинает новую нативную
ветку, чтобы будущие сообщения старой ветки не попали в ответ.

Совместимая завершённая сессия восстанавливается через ACP `session/load` после
reload. Повторно проигрываемая сервером история не показывается как новый ответ.
Изменившийся каталог client tools обновляется через load; отменённая или
незавершённая сессия не считается завершённой контрольной точкой.
При смене провайдера отменяется только ожидающий цикл того же conversation ID.
Другие чаты и завершённые тёплые сессии сохраняются.

## Очень большая история

Исполняемый путь больше не удаляет середину разговора ради общего ограничения
в 500 000 символов. История переносится целиком в ограниченных по размеру
ACP-запросах. Между ними Coco сохраняет состояние и при необходимости применяет
своё нативное сжатие. Во время импорта действия запрещены, ответы ACK скрыты.
После переноса выполняется последний пользовательский запрос.

Полный текст и изображения дополнительно сохраняются локально; путь к транскрипту
доступен модели для точечного перечитывания. Большой tool result возвращает
ограниченный preview и путь к полному выводу вместо безвозвратного удаления
середины. Исторические запросы и инструменты передаются как данные разговора.

Каждый запрос также содержит путь к текущему полному JSON-журналу Chat, включая
последующие тёплые ходы и результаты инструментов. Поэтому после сжатия модель
может перечитать точные детали не только из первоначального холодного архива.

Каждый импортный запрос расходует токены. Число дополнительных запросов
ограничено `llamacpp.cocoMaxHistoryImportParts` (16 по умолчанию). Если требуется
больше, генерация не начинается: Chat сообщает число частей и путь к полному
транскрипту. Можно компактировать исходный Chat либо явно разрешить больший
лимит, учитывая стоимость. Дополнительные запросы входят в usage текущего хода.

`claude-opus-5-5` получил проверенный начальный лимит 1 000 000 токенов.
Он задаётся в `llamacpp.cocoModelContextLengths`; для неизвестных моделей
остаётся общий fallback 128 000. Реальная `usage_update.size` имеет приоритет
и сохраняется с совместимой контрольной точкой. Бюджет переноса отдельно
резервирует схемы инструментов и нативные инструкции/skills CLI.

Это не бесконечная память: нативная суммаризация конечного окна может упрощать
детали. Для восстановления точных формулировок остаётся полный транскрипт.
Журнал также не восстанавливает сообщения, которые были утрачены до обновления
и ни разу не передавались расширению. Неподдерживаемые бинарные вложения нужно
предоставлять извлечённым текстом или читать через инструменты; они не
выбрасываются молча из нового пути импорта.

## Реальные cache hits и диагностика

Ответ ACP `session/prompt` содержит `usage`:

- `inputTokens`: новые входные токены без cache read/write;
- `cachedReadTokens`: чтение кеша;
- `cachedWriteTokens`: запись кеша;
- `outputTokens`: выходные токены.

Общий вход = `inputTokens + cachedReadTokens + cachedWriteTokens`.
Cache hit = `cachedReadTokens / общий вход`. Уже включённый кеш повторно
не прибавляется. Проценты не выводятся из факта тёплой сессии.

Счётчики видны в диагностике с `providerKind: coco`, в карточке Coco и отдельной
категории Token Usage. Учитываются также импортные запросы. `usage_update.used`
и `size` описывают занятое окно, поэтому они не суммируются как биллинг.
Количество сегментов здесь означает завершённые ACP prompts, а не неизвестное
число внутренних обращений CLI к модели. Служебная фоновая работа, не отражённая
в ACP usage, не подменяется оценками.

Если старый runtime не отдаёт счётчики или часть сегментов не отчиталась,
диагностика отмечает неполноту и не показывает выдуманный нулевой cache read.
Время жизни кеша, маршрутизация и eviction зависят от Snowflake/модели.
Сохранённая сессия позволяет переиспользовать префикс, но не гарантирует cache hit.

## Что проверено на настоящей модели

Прямой тест клиента выполнил три коротких запроса к Opus 5.5 без инструментов:
создание сессии, тёплый запрос, новый процесс CLI с восстановлением. Контрольный
факт сохранился. Runtime сообщил окно 1 000 000. Cache read составил примерно
99,96% на тёплом запросе и 99,67% после восстановления.

Дополнительный тест прошёл через реальный Coco provider и общий маршрутизатор:

1. Codex-фикстура записала требования и находку в журнал.
2. Вход Coco намеренно не содержал ранних сообщений. Журнал восстановил их;
   малый тестовый бюджет заставил выполнить реальный перенос частями.
3. Opus вернул маркеры из начала, середины и последнего ответа Codex.
4. Тёплый запрос и восстановление после reload также сохранили все три маркера.

| Ход | Обработанный вход | Cache read | Доля чтения | ACP prompts |
|---|---:|---:|---:|---:|
| Холодный перенос | 189 130 | 125 260 | 66,23% | 3 |
| Тёплое продолжение | 64 508 | 63 862 | 99,00% | 1 |
| После reload | 64 998 | 64 506 | 99,24% | 1 |

Это измерения конкретных синтетических тестов, не обещание таких процентов
для каждого рабочего запроса. Реальный Codex в тесте не вызывался: его видимый
вклад моделировала фикстура, а Coco/Opus и восстановление были настоящими.

Для повторения прямого теста после компиляции есть
`node scripts/coco-session-smoke.mjs --run` с опциями `--cli`, `--connection`
и `--model`. Без `--run` он не вызывает модель. Полный integration test
включается переменной `AAB_COCO_REAL_CONTINUITY=1` и путём к CLI в
`AAB_COCO_CLI`, затем запускается `npx vscode-test --grep 'Coco real runtime'`.
Оба сценария используют реальные модельные запросы; по умолчанию CI их пропускает.

## Хранение и границы

Журнал `chat-history` и архивы `coco-history` находятся в workspace storage
расширения, вне репозитория. Они содержат видимый текст чатов, результаты
инструментов и вложения. Ключи имён файлов хешированы. Записи журнала
атомарны; параллельный старый ответ не перезаписывает более новый.
Максимальный размер одного журнала — 64 MiB; превышение явно останавливает
перенос. Удаление workspace storage удаляет и эти локальные копии.

В `workspaceState` сохраняются только нативные session IDs, хеши якорей
истории, время и измеренное окно. Контрольная точка незавершённого запроса
не восстанавливается. Одновременно удерживаются до восьми незанятых тёплых
процессов; простаивающий процесс закрывается через 30 минут. До 32 контрольных
точек хранятся семь дней. Текст нативных сессий хранит сам CLI Snowflake.

Ошибка локального журнала не блокирует Codex/Claude/HTTP; для Coco она
сообщается явно, чтобы незаметно не продолжить разговор с урезанной историей.
Смены модели, workspace и connection изолированы. Результаты устаревших
вызовов инструментов отклоняются вместо повторного исполнения.
